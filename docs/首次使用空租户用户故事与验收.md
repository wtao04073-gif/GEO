# 首次使用空租户用户故事与验收

## 1. 用户故事

作为首次使用 GEO 运营系统的区域品牌运营人员，我希望登录一个没有业务演示数据的新租户后，能清楚理解系统当前为空、从首页或品牌工作台创建第一个品牌，并在创建成功后直接进入该品牌的工作上下文，以便继续完善品牌事实、规划内容和建立观测任务，而不会遇到空品牌请求、错误页或不知下一步做什么的断点。

## 2. 角色与前置条件

### 角色

- 主角色：租户内具有品牌创建权限的运营人员。
- 隔离校验角色：另一个测试租户中的运营人员。

### 前置条件

- 自建应用、本地 Keycloak 与两个测试租户均已启动。
- 主租户没有品牌、品牌事实、内容任务、发稿记录、观测任务、模拟证据和业务线索。
- 隔离租户的数据状态独立。
- 系统配置、渠道能力和必要字典可用。
- 真实渠道授权未配置；本流程不依赖真实发稿与正式观测入口。
- 浏览器不存在一个仍可用于当前租户的历史选中品牌；即使残留旧品牌 ID，系统也应自动判无效并回到空状态。

## 3. 主流程

1. 用户以主租户运营人员身份登录。
2. 系统进入首页，识别当前租户没有品牌。
3. 首页展示明确的首次使用空状态，包括：为什么当前为空、创建首个品牌的主操作、创建后可以继续完成的事项。
4. 用户点击“创建品牌”。
5. 系统打开品牌创建表单；用户填写最小必填信息。
6. 用户提交表单。提交期间按钮进入忙碌状态，阻止重复提交。
7. 创建成功后，系统刷新品牌列表，并将新品牌设置为顶部全局筛选器的当前品牌。
8. 系统进入或刷新品牌工作台，以新品牌 ID 请求数据；不得先发起空品牌 ID 请求。
9. 品牌工作台展示新品牌的合法空状态，并给出后续动作，例如完善品牌事实、创建内容任务或配置观测。
10. 用户刷新页面，当前品牌仍可被正确恢复；若产品约定不持久化上次选择，则至少应选择租户内唯一品牌，不能退回错误态。
11. 用户退出并重新登录，服务重启后再次访问，已创建品牌仍存在，“青溪古镇”等演示业务数据不会恢复。

## 4. 入口连续性要求

- 首页空状态与品牌工作台空状态至少有一个清晰、可用的首个品牌创建入口。
- 两个入口若同时存在，应进入同一个创建流程，字段和校验一致。
- 未创建品牌前，页面不得用通用错误页、接口报错提示或无限加载覆盖创建入口。
- 创建成功后，不要求用户手动刷新或再次从顶部筛选器选择刚创建的品牌。
- 新品牌工作台应区分“品牌存在但尚无业务数据”和“系统加载失败”。前者使用引导型空状态，后者使用可重试错误态。

## 5. 异常分支

### 5.1 表单校验失败

- 缺少必填信息时在字段附近提示原因，不提交请求。
- 用户已填写的其他内容保留。
- 修正后可以继续提交。

### 5.2 品牌名称重复或业务规则冲突

- 展示具体、可行动的冲突原因。
- 不创建重复品牌，不切换全局品牌筛选器。
- 用户修改后可以再次提交。

### 5.3 创建请求失败

- 页面保留表单数据并提供重试。
- 全局品牌筛选器仍保持无选择状态。
- 不把失败记录渲染成已创建品牌。

### 5.4 创建成功但后续工作台加载失败

- 系统不得回滚或重复创建已经成功的品牌。
- 顶部筛选器显示已创建品牌。
- 工作台展示加载失败与重试入口；重试使用已创建品牌 ID。

### 5.5 重复点击或网络重试

- 前端提交期间禁用重复提交。
- 后端按现有业务唯一性或幂等规则避免生成重复品牌。

### 5.6 历史品牌选择失效

- 本地保存的品牌不属于当前租户、已删除或不存在时，清除该选择。
- 若租户没有品牌，进入首次使用空状态。
- 若租户已有品牌，按产品既有规则选择合法品牌。
- 不以失效品牌 ID 请求品牌域接口。

### 5.7 租户切换

- 切换到另一个租户后，重新计算该租户的品牌列表与当前选择。
- 不沿用原租户的品牌 ID、缓存数据或工作台内容。
- 主租户新建品牌在另一个租户不可见。

### 5.8 权限不足

- 无品牌创建权限的用户看到说明性空状态，不展示不可执行的主按钮，或点击后得到明确权限提示。
- 不通过隐藏按钮之外的方式绕过后端权限校验。

## 6. 验收结果

### A. 数据基线

- 运行态数据库中不存在“青溪古镇”等业务演示数据。
- 系统配置、渠道能力、必要字典、双租户与登录用户仍可用。
- 服务与依赖整体重启后，演示业务数据不会重新出现。
- 测试 fixtures 保留，测试可独立建立所需数据。

### B. 首次进入

- 空租户登录后首页正常渲染，不出现错误页或无限加载。
- 创建首个品牌的入口在首屏或清晰的一步导航内可达。
- 无选中品牌时，网络请求中不存在空品牌 ID、`undefined` 品牌 ID 或跨租户品牌 ID。

### C. 创建品牌

- 合法输入只创建一个品牌。
- 成功反馈明确，品牌列表立即包含新品牌。
- 顶部筛选器自动选中新品牌。
- 工作台使用新品牌 ID 加载，并展示品牌级合法空状态。

### D. 错误恢复

- 校验失败、业务冲突、网络失败均保留可恢复路径。
- 创建成功后的详情加载失败不会诱导重复创建。
- 页面刷新、重新登录和服务重启后状态符合持久化约定。

### E. 租户隔离

- 在租户 A 创建的品牌不会出现在租户 B。
- 租户切换后不会使用原租户的品牌 ID 发起请求。
- 后端接口对跨租户品牌访问继续执行现有权限与归属校验。

### F. 业务约束

- 未接入真实渠道时，系统仍明确区分 Mock、人工证据和正式授权状态。
- 不因首用流程而放宽真实渠道授权、发稿、观测或证据校验。

## 7. 建议的自验证顺序

1. 检查运行态数据清理脚本或迁移，并搜索所有自动种子入口。
2. 冷启动全部本地依赖，确认两个租户均能登录。
3. 在主租户从首页完整走通创建首个品牌。
4. 观察网络请求，确认创建前无品牌域空 ID 请求，创建后所有请求使用新品牌 ID。
5. 刷新、重新登录并重启服务，核对状态持久化和演示数据不回灌。
6. 切换到第二租户，核对品牌与缓存隔离。
7. 分别模拟表单校验失败、创建接口失败、创建后工作台加载失败和重复点击。
8. 以固定并发 `2` 运行全仓测试、类型检查和构建，核对历史基线 `169` 项通过、`3` 项跳过。

## 8. 完成定义

只有同时满足以下条件，本项才可视为完成：

- 运行态业务演示数据已清理且重启不回灌。
- 首页到创建首个品牌再到品牌工作台的主流程连续可用。
- 异常分支至少完成自动化覆盖或可复现的人工验证记录。
- 双租户隔离验证通过。
- 全仓测试、类型检查和构建在受控并发下通过。
- 实际代码、文档和测试结果已提交到 `main` 或形成可合并变更。
