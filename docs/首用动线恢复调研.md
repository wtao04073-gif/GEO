# 首用动线恢复调研

## 1. 调研摘要

本轮目标是接续“清空演示数据 + 首次进入系统的完整首用动线”，而不是重新设计 GEO 运营系统。当前已知产品定位、业务边界和中断点足以整理用户故事与验收口径，但代码仓库暂时不可访问，因此无法核对实际页面、接口、提交记录和测试基线。

恢复检查结果：

- 当前工作区没有代码仓库。
- 当前项目的 Context、Memory 与历史 Session 范围内，没有检索到原任务正文或仓库副本。
- 当前 Codebase 登录身份有效。
- `wang.1022/geo-ops-platform` 在 Codebase 返回仓库不存在；SSH 与 HTTPS 拉取均失败。
- 本机其他 Worker 目录中未找到 `geo-ops-platform` 副本。

## 2. 用户与场景

目标用户是首次为一个非中心城市或县域品牌建立 GEO 运营空间的运营人员。用户第一次进入系统时，租户内没有任何业务品牌、内容、观测任务、证据或线索数据；系统应通过连续的空状态引导，让用户建立第一个品牌并进入可继续工作的品牌工作台。

核心痛点不是“没有演示数据可看”，而是空租户容易暴露隐式前提：页面默认假设一定存在品牌、全局筛选器默认一定有选中值、下游请求可能携带空品牌 ID。首用体验必须把“没有品牌”作为合法业务状态。

## 3. 已知现状

- 运行态需要清理“青溪古镇”等业务演示数据。
- 系统配置、渠道能力和必要字典需要保留。
- 服务重启后不得重新灌入业务演示数据。
- 测试夹具保留不动。
- 已修复：无选中品牌时，品牌工作台不再请求空品牌 ID，错误态不再遮挡首次创建入口。
- 已修复：品牌创建成功后，顶部品牌筛选自动切换到新品牌。
- 真实渠道授权尚未就绪，仍采用本地 Mock、Keycloak 双租户和人工/模拟证据。

## 4. 业务规则与边界

- 空租户是正常状态，不是系统错误。
- 未选择品牌时，品牌域接口不得以空字符串、`undefined` 或占位 ID 发起请求。
- 创建成功后，新品牌应成为当前租户、当前会话的选中品牌。
- 租户 A 创建的品牌不得出现在租户 B 的列表、筛选器、工作台或接口结果中。
- 清空业务数据不得删除系统配置、渠道能力、必要字典、Keycloak 租户与用户。
- 运行时初始化不得自动恢复演示业务数据。
- 测试夹具属于测试隔离数据，不因清理运行态演示数据而删除。
- Mock 或模拟证据必须保持现有业务校验，不以“首用可通过”为由降低授权或证据可信要求。

## 5. 风险与异常角落

- 首页和品牌工作台可能各自维护一套空状态，导致入口文案或跳转目标不一致。
- 品牌创建成功后，列表缓存、全局筛选状态和工作台查询的刷新顺序可能产生短暂空白或旧品牌闪现。
- 创建接口成功但后续详情查询失败时，不应让用户误以为创建失败并重复提交。
- 双击提交、网络重试或名称重复可能产生重复品牌。
- 切换租户后若复用浏览器本地选中品牌，可能造成跨租户品牌 ID 泄漏或错误请求。
- 数据清理若仅修改一次性数据库而未移除启动种子逻辑，重启后演示数据会复现。

## 6. 待仓库恢复后核对

- 最近提交是否已经包含两项已知修复，以及具体影响文件。
- 空状态首页、品牌工作台、创建表单和顶部筛选器的实际路由与组件名。
- 演示数据来源是迁移、启动种子、开发脚本还是容器初始化。
- 双租户的实际名称、用户角色和本地登录方式。
- 全仓测试、类型检查、构建命令及历史 `169` 项通过、`3` 项跳过的统计口径。
- 品牌创建失败、重复提交、租户切换与服务重启是否已有自动化覆盖。
